# orch-test: multi-agent orchestration demo

Several headless Claude Code agents build a Go API in parallel.
- **Backend:** designed with **DDD**, structured as a **hexagonal architecture**, written **test-first**, and stored in **MongoDB 8**.
- **API:** specified in OpenAPI 3, with server and client code generated by [ogen](https://ogen.dev).
- **Frontend:** Vue + TypeScript, coming later.

You describe a feature as a **story**. A planner agent breaks it into tasks, and worker agents implement them in parallel, each in its own git worktree. A quality gate checks every branch before the orchestrator merges it into the story's own branch, `story/<plan>`. When the story is done, the combined result is checked once more, and the branch is yours to review and push. Your checkout is never touched. You decide at a few checkpoints along the way.

## Quick start

Requires `python3`, `go` (1.27+), `git`, `claude` (Claude Code, logged in) and Docker.

```bash
git add -A && git commit -m "Initial scaffold"   # story branches start from your last commit

# Tests and gates need MongoDB
make mongo && export MONGO_TEST_URI=mongodb://localhost:27017

# Keep the dashboard open in a second terminal: it shows progress and tells you the next step
make dashboard   # http://localhost:8765/orchestration/dashboard/

# Write a story (copy backlog/stories/TEMPLATE.md), let the planner turn it into a plan, review it
make plan STORY=backlog/stories/s-04-my-feature.md   # writes backlog/plans/s-04-my-feature.json

# Rehearse without calling Claude (no cost): fake agents, real queue, worktrees and merges
make dry-run PLAN=backlog/plans/s-04-my-feature.json   # merges placeholders into story/s-04-my-feature
git branch -D story/s-04-my-feature && make reset      # clean up the rehearsal

# The real thing
make load PLAN=backlog/plans/s-04-my-feature.json && make run
```

`backlog/` holds the stories and plans built so far (`s-01-db-schema`, `s-02-crud-on-books-api`, `s-03-remove-in-memory`); they are good examples to copy from.

## Using the orchestrator

The orchestrator is a Python CLI (`orchestration/orchestrator/orchestrator.py`, standard library only). The `make` targets are shortcuts for it, so use whichever you prefer:

| `make` | CLI (`python3 orchestration/orchestrator/orchestrator.py …`) | What it does |
|---|---|---|
| `make plan STORY=backlog/stories/S02-x.md` | `plan backlog/stories/S02-x.md` | The planner agent turns a story into a plan file, `backlog/plans/S02-x.json`. Nothing is queued yet |
| `make load PLAN=backlog/plans/S02-x.json` | `load <plan>` | Queues the plan's tasks |
| `make run` | `run [--workers N]` | Starts workers until nothing runnable is left, merging into `story/<plan>`; finalizes finished stories; serves the dashboard |
| `make run ONLY=S02-01,S02-02` | `run --only S02-01,S02-02` | Runs only these tasks (e.g. the spec phase) |
| `make dashboard` | `dashboard` | Live dashboard on http://localhost:8765/orchestration/dashboard/, with or without a run. Leave it open |
| `make status` | `status` | Every task and its state; errors for failed ones |
| `make proposals` | `proposals` | Follow-up tasks agents proposed, e.g. security fixes |
| `make review` | `review` | Goes through the waiting proposals one by one (task text collapsed; t shows it): approve, reject, skip, chat with Claude about it (and have it adjust the proposal), or quit |
| `make approve IDS="S02-07.1"` | `approve <ids>` | Queues proposals, including parked ones; they run on the next `make run` |
| `make reject IDS="S02-07.2"` | `reject <ids>` | Discards proposals |
| `make retry` / `make retry IDS="S02-03"` | `retry [ids] --run` | Puts failed tasks back in the queue with fresh attempts and starts a run for their plans. Without `IDS`: every failed task of the stories started from your current branch. `NORUN=1` only requeues |
| `make reset` | `reset` | Deletes runtime state (`.orch/`, `.worktrees/`, `agent/*` branches). Keeps stories, plans and `story/*` branches |
| `make dry-run PLAN=backlog/plans/S02-x.json` | `load <plan>` + `run --fake` | Rehearses a plan without calling Claude (see [Dry runs](#dry-runs)) |

### Workflow: story → plan → spec → implementation

You stay in charge at three checkpoints: the **plan**, the **spec** and the **proposals**. Between them, agents work in parallel without you.

```
 you          write story ──▶ review plan ──────────▶ review spec ─────────────▶ approve proposals ──▶ ship
                  │               ▲    │                 ▲    │                      ▲     │
 agents           └─ planner ─────┘    └─ phase 1: spec ─┘    └─ phase 2: adapters, ─┘     └─ fixes
                                          + domain model         storage, e2e, docs,
                                          + spec review          hardening review
```

1. **Write a story** in `backlog/stories/S<NN>-<slug>.md` (copy `backlog/stories/TEMPLATE.md`). The story describes the *what*, in the domain's language:
   - the user story;
   - the bounded context;
   - domain terms and rules;
   - acceptance criteria;
   - what's out of scope.
2. **Plan it:** `make plan STORY=…` writes `backlog/plans/S<NN>-<slug>.json`, with task IDs `S<NN>-01`, `S<NN>-02` and so on. **Review it before anything runs.** Check that each task's scope is narrow, that the dependencies make sense, and that every acceptance criterion has a test. The file is plain JSON, so edit it as needed.
3. **Queue it:** `make load PLAN=…`. Commit the story and the plan to your branch whenever you like; `run` doesn't need a clean tree, because agents work on `story/<plan>`, which starts from your last commit.
4. **Phase 1, the spec:** `make run ONLY=<api task>,<model task>,<spec review>`. The domain model doesn't depend on the spec, so it is built test-first at the same time.
5. **Review the spec** on the story branch. While the story is in progress, it's checked out in `.worktrees/_story-<plan>`:
   - `git log --oneline main..story/<plan>`, then `git show` the spec merge;
   - read `.worktrees/_story-<plan>/backend/api/openapi.yaml`;
   - read the security spec review in `.worktrees/_story-<plan>/docs/security/`;
   - run `make proposals`.

   This is the cheapest moment to change your mind. Edit the spec yourself in that worktree (then `make generate` there and commit), or approve the proposed spec fixes. Later tasks start from the story branch, so they pick up your changes.
6. **Phase 2, implementation:** `make run` runs everything else, including the HTTP adapter, MongoDB storage, e2e tests for the acceptance criteria, docs and the hardening review.
7. **Decide on proposals:** `make review` (one by one), or `make proposals`, then `approve` or `reject`; then `make run`. Repeat until nothing important is left.
   - Only `critical` and `high` proposals, and proposals without a severity, wait for you. `"auto_decide"` in `orchestration/config.json` settles the rest: `medium` is approved and runs in the same `make run`, and `low` is **parked**. A parked proposal is stored as rejected, so it doesn't hold up the story. The dashboard shows it as "parked", and `make approve` still queues it. An automatic approval is held back for you if the proposal depends on one that waits for you or was parked.
8. **Lead review and one commit:** when no task of the plan is left to run, `make run` finalizes the story:
   - it runs all checks on the combined `story/<plan>`;
   - the **lead engineer** agent (`roles/lead.md`) reviews the whole change like a pull request: does it deliver the story, do the separately built tasks fit together, architecture, tests, docs. It changes nothing. It returns a verdict (`approve` or `changes_requested`), a report in `.orch/reviews/<plan>.md`, fix proposals for every blocking finding, and the commit message;
   - it releases the branch and squashes the story into **one commit on `pr/<plan>`** with the lead's message. `story/<plan>` keeps the per-task history;
   - if the lead approved and every check passed, it **fast-forwards the branch you started from** (the one you ran `make run` on) onto that commit. That's never a merge commit, and nothing is pushed. It is skipped, with the reason on the story card, if that branch got new commits meanwhile, or if your uncommitted or untracked files would be overwritten (git changes nothing then). Turn it off with `"merge_into_base": false` in `orchestration/config.json`;
   - it prints the review and push commands, which the dashboard also shows on the story card.

   If the lead requested changes, `make review` the proposals and `make run` again: the story reopens, and when it's done the lead reviews it again and `pr/<plan>` is rebuilt. If the story was already merged and your branch has nothing newer, the fixes come as one more commit on top, which is merged the same way.
9. **Ship:** read the review, try it (`make up`), and `git push`. If it wasn't merged automatically: `git switch pr/<plan>` and push that, or merge it yourself.

**Variations**
- **Small story:** skip the spec checkpoint, `make load` and then a single `make run`.
- **API design session:** plan the story, then only ever run the api task and its spec review, and iterate on the spec with proposals until it's right.
- **Fix-up round:** for a bug, write a tiny story ("Given …, when …, then …") and plan it like any other.

### Example: a shopping list

**1. Story:** `backlog/stories/S02-shopping-list.md`

```markdown
# S02: Shopping lists

## Story
As a household member, I want shared shopping lists, so that we buy everything we need exactly once.

## Domain
- **Bounded context:** `shopping` (new)
- **Terms:** a *shopping list* has a *name* and *items*; an item has a *product name* and a *quantity*;
  items are *added*, *checked off* and *removed*; a list is *cleared* of checked-off items.
- **Rules:**
  - A list name is 1–100 characters; a product name 1–100 characters; quantity 1–99.
  - Adding a product that is already on the list increases its quantity instead of adding a duplicate.
  - Checked-off items can't change quantity.

## Acceptance criteria
- [ ] When I create a list "Weekend", then it exists with no items.
- [ ] When I add "Milk" ×2 and then "milk" ×1, then the list has one item "Milk" ×3.
- [ ] When I add an item with quantity 0 or 100, then I get 400.
- [ ] Given a checked-off item, when I change its quantity, then I get 409.
- [ ] When I clear the list, then only unchecked items remain.
- [ ] Unknown lists and items give 404.

## Out of scope
- Authentication, sharing permissions, prices.
```

**2. Plan:**

```bash
make plan STORY=backlog/stories/S02-shopping-list.md
```

The planner prints the plan it wrote. A typical result looks like this; yours will differ, which is why you review it:

```
Wrote 8 task(s) to backlog/plans/S02-shopping-list.json:
  S02-01   [api]       Shopping list API spec
  S02-02   [backend]   Shopping domain model and use cases (TDD)
  S02-03   [security]  Security review: shopping spec  (after S02-01)
  S02-04   [backend]   Shopping HTTP adapter and wiring  (after S02-01, S02-02)
  S02-05   [backend]   Shopping MongoDB repository  (after S02-02, S02-04)
  S02-06   [tests]     E2E tests for the acceptance criteria  (after S02-04)
  S02-07   [security]  Security review: shopping context  (after S02-04, S02-05)
  S02-08   [docs]      Shopping list documentation  (after S02-04, S02-05)
```

Open the JSON and check it. For example: is the "merge duplicate products" rule in S02-02's prompt? Does S02-06 quote every acceptance criterion? Is S02-02's scope limited to `internal/shopping/{domain,app}`?

**3. Queue it** (and commit the story and plan to your branch whenever you like):

```bash
make load PLAN=backlog/plans/S02-shopping-list.json
```

**4. Phase 1, spec and model:**

```bash
make run ONLY=S02-01,S02-02,S02-03
```

**5. Review the spec:**

```bash
git log --oneline main..story/S02-shopping-list      # Merge S02-01 …, Merge S02-02 …, Merge S02-03 …
cd .worktrees/_story-S02-shopping-list               # the story branch, checked out while in progress
less backend/api/openapi.yaml
less docs/security/S02-03-*.md                       # e.g. "SEC-1: listShoppingLists is unbounded"
make check                                           # do the merged parts work together?
cd - && make proposals
```

```
S02-03.1  [medium] Paginate listShoppingLists  — role api, from S02-03
    why:   SEC-1: unbounded list response
    …
```

```bash
make approve IDS=S02-03.1      # or: make reject IDS=S02-03.1, or edit the spec in the story worktree and commit
```

**6. Phase 2, everything else** (S02-03.1 runs too, since it's now queued):

```bash
make run
```

**7. Proposals from the hardening review:**

```bash
make proposals                 # e.g. S02-07.1 [medium] Limit request body size
make approve IDS=S02-07.1 && make run
```

**8. Ship.** The last `make run` finalizes the story and prints:

```
Story S02-shopping-list is complete on branch story/S02-shopping-list: 24 commits, 31 files changed, all checks passed.
Review and push it yourself:
  git log --oneline --graph main..story/S02-shopping-list
  git diff --stat main...story/S02-shopping-list
  git switch story/S02-shopping-list && make check      # try it, e.g. make up
  git push -u origin story/S02-shopping-list            # then open a pull request
```

```bash
git switch story/S02-shopping-list && make up
curl -s -X POST localhost:8000/api/shopping-lists -d '{"name":"Weekend"}' -H 'Content-Type: application/json'
git push -u origin story/S02-shopping-list
```

### Monitoring and troubleshooting

- **Dashboard:** run `make dashboard` in a second terminal and keep http://localhost:8765/orchestration/dashboard/ open. `make run` serves it too, while it runs.
  - **What now?** The next step, with the exact command to copy. It covers: load a plan, commit first, MongoDB is down, `MONGO_TEST_URI` is missing from the run, run stage 1 and review it, a task failed so retry it, proposals are waiting, or everything is merged so check it.
  - **Planner:** while `make plan` runs, the files it read and its thinking-token count. If those numbers grow, it isn't hung.
  - **Tasks by stage:** stages come from the dependencies, and proposals have their own lane. Each card shows status, model and effort, duration and cost, and the agent's current tool call.
  - **Click a task** for its prompt, scope, dependencies, errors and the agent's step-by-step log for every attempt.
- **`make status`:** a failed task shows the gate or agent error.
  - **Attempts:** every task gets `max_attempts` (2), each in a fresh worktree.
  - **Retry:** after fixing the cause (an unclear prompt in the plan, a wrong scope, …), `make retry` (all failed tasks of this branch) or `make retry IDS=…`; it starts the run itself.
- **Logs:**
  - `.orch/logs/<task>.attempt<N>.jsonl` is the raw Claude stream (every tool call and its result);
  - `.orch/events.jsonl` is the orchestrator's event log.
- **Stuck queue:** `run` stops when nothing runnable is left. If tasks are still pending, a dependency failed; check `make status`.
- **Ctrl-C** stops the workers. Interrupted tasks go back to pending on the next `run`.
- **MongoDB tests:** tests need MongoDB, and `backend/check.sh` fails without `MONGO_TEST_URI`. Agents and gates inherit your environment, so start the database and export it before `make run`:

  ```bash
  make mongo && export MONGO_TEST_URI=mongodb://localhost:27017
  ```

### Dry runs

`--fake` workers don't call Claude. They write a placeholder file inside each task's scope, skip the gate commands, and security tasks propose a fake follow-up. This exercises the queue, dependencies, `--only`, proposals, merges and story finalization at no cost (the final checks are skipped). The placeholders end up on `story/<plan>`, so delete that branch afterwards:

```bash
make dry-run PLAN=backlog/plans/<plan>.json    # or: make load PLAN=… && python3 orchestration/orchestrator/orchestrator.py run --fake
git branch -D story/<plan> && make reset
```

## How it works

### Layout

```
orch-test/
├── CLAUDE.md          rules every agent reads
├── docker-compose.yml MongoDB 8 + backend
├── backlog/           your input; agents never touch it
│   ├── stories/          one story per feature (TEMPLATE.md, s-01-db-schema.md, …)
│   └── plans/            plan files from `make plan`, named after their story (s-01-db-schema.json, …)
├── backend/           Go 1.27 module                       ┐
│   ├── api/openapi.yaml   API contract (source of truth)   │
│   ├── internal/<context>/ bounded context = hexagon       │
│   ├── internal/oas/      ogen-generated server + client   │
│   ├── internal/handler/  embeds the contexts' adapters    │ the product
│   ├── internal/bootstrap/ composition root, MongoDB wiring│ agents work on
│   ├── internal/archtest/ dependency rules as a Go test    │
│   ├── internal/platform/mongodb/ MongoDB connection       │
│   ├── e2e/               tests via generated oas.Client   │
│   ├── Dockerfile         distroless image                 │
│   └── check.sh           every backend check (the gate)   │
├── frontend/          reserved for Vue 3 + TS              │
├── docs/              written by agents (docs/security/: reviews)
│
├── orchestration/     everything that runs the agents; agents never touch it
│   ├── config.json       workers, model, allowed tools, gates, TDD rule
│   ├── orchestrator/     Python 3 stdlib, no deps
│   │   ├── orchestrator.py   CLI: plan, load, run, status, proposals, approve, reject, retry, reset
│   │   ├── worker.py         claim task → `claude -p` in worktree → commit → gate → collect proposals
│   │   ├── tasks.py          file-based queue (atomic rename = claim)
│   │   ├── worktrees.py      one worktree + branch per task
│   │   └── quality_gate.py   scope check, TDD check, gate commands
│   ├── roles/            role prompts: planner, lead, api, backend, tests, security, docs, frontend
│   └── dashboard/        live view, served by the orchestrator
│
├── .orch/             runtime state (gitignored)
└── .worktrees/        agent checkouts (gitignored)
```

### Task lifecycle

```
proposed ──approve──▶ pending ──claim──▶ claimed ──agent + commit + gate ok──▶ passed ──merge──▶ done
   │                     ▲                  │                                     │
   └─reject─▶ rejected   └──── requeue ──── failed ◀──── gate / agent error ──────┘ (merge conflict)
```

- A task is claimable once every task in its `depends_on` is `done`, so dependent work always starts from merged code.
- Workers claim tasks atomically. Each task runs `claude -p` with the task's role prompt in a fresh worktree on branch `agent/<id>`, which starts from its story branch.
- **Story branches:** each plan's passing tasks are merged one at a time into `story/<plan>`, in an integration worktree (`.worktrees/_story-<plan>`). Your checkout and `main` are never touched, and the story branch starts from your last commit.
- **Finalizing:** once no task of the plan is left to run, `make run` checks the combined branch with every gate, removes the integration worktree (so you can `git switch` to the branch), and prints the review and push commands. Proposals still waiting don't hold the branch; approving one reopens it on the next run.
- Agents can't commit or touch anything outside their scope. Work they think is needed elsewhere becomes a **proposal**, which waits in `proposed` for you.

### Quality gate

Every task branch has to pass these checks before it's merged:

| Check | Where |
|---|---|
| Changed files are within the task's `scope` globs | `quality_gate.py` |
| TDD: a change in `internal/*/domain` or `internal/*/app` comes with a `_test.go` change in the same package | `quality_gate.py` (`require_tests_for` in `config.json`) |
| `internal/oas` matches the spec (no hand edits, no forgotten `go generate`) | `backend/check.sh` |
| gofmt, go vet | `backend/check.sh` |
| Tests, including `internal/archtest` (hexagonal and bounded-context dependency rules) | `backend/check.sh` |
| At least 80% coverage in domain and app packages (`MIN_COVERAGE`) | `backend/check.sh` |
| `gosec` (static analysis) and `govulncheck` (known vulnerabilities in called dependencies) | `backend/check.sh` |

Agents run `backend/check.sh` themselves before finishing, so most failures are fixed before the gate ever sees them. `make check` runs it on your checkout.

The gate checks each task branch on its own. When a story is finalized, all gates run once more on the combined story branch. That catches problems that only appear when parallel tasks come together, such as two tasks declaring the same function in one Go package. The result appears in the summary and on the dashboard.

### Roles

| Role | Does | Typical scope |
|---|---|---|
| `planner` | Story → plan; never writes code | (none) |
| `api` | OpenAPI spec + `go generate` | `backend/api/**`, `backend/internal/oas/**` |
| `backend` | DDD model and use cases test-first, adapters, wiring | `backend/internal/<context>/…` |
| `tests` | e2e tests for the acceptance criteria, via the generated client | `backend/e2e/**` |
| `security` | Threat model, findings, security regression tests; fixes come back as proposals. Never blocks merges | `docs/security/**`, `backend/e2e/security_*_test.go`, infrastructure files |
| `docs` | Documentation from the actual code | `docs/**` |
| `frontend` | Vue 3 + TS (once `frontend/` exists) | `frontend/**` |

Authentication and authorization are out of scope for the demo. Security reviews record them once as an accepted risk.

### Models

The orchestrator chooses the model for each agent:

| Who | Model | How it's chosen |
|---|---|---|
| Planner | Claude Opus 5.5 (`claude-opus-5-5`, effort `xhigh`) | Always. One call per story, and the plan's quality decides everything after it |
| Workers | Claude Haiku 5.5 (`claude-haiku-5-5`), Claude Sonnet 5.5 (`claude-sonnet-5-5`) or Claude Opus 5.5 (`claude-opus-5-5`) | The planner sets `"model"` (`haiku`, `sonnet`, `opus`) and `"effort"` (`low`, `medium`, `high`, `xhigh`) on every task |
| Lead engineer | Claude Opus 5.5 (`claude-opus-5-5`, effort `high`) | `models.lead`: one review per finished story. Remove the entry to skip the review (the story is still squashed) |
| Review chat | Claude Sonnet 5.5 (`claude-sonnet-5-5`, effort `high`) | `models.reviewer`: the `[c]hat` option in `make review`. Falls back to the planner model if unset |

- **`haiku`:** mechanical, fully specified tasks, such as wiring per exact instructions, docs from code, or small fixes. It costs about a twentieth of Sonnet.
- **`sonnet`:** anything that needs judgment, such as spec design, the DDD model written test-first, adapters with real logic, e2e tests, or security reviews. Most tasks use it, and a task without a model gets it.
- **`opus`:** the few tasks per story where depth of reasoning decides the outcome, at about twice Sonnet's price. Examples: a domain model with many interacting invariants, tricky concurrency or consistency logic, cross-context changes, an end-to-end threat model. In the demo plan, that's T-010, the hardening review.
- **Effort:** the planner always chooses one.
  - `low` for trivial edits, and `medium` for well-specified routine work;
  - `high` for normal engineering with design decisions;
  - `xhigh` only when a subtle mistake would be costly (T-010 runs `opus/xhigh`).

  Typical pairings are `haiku/medium`, `sonnet/high` and `opus/high`. If a plan omits an effort, `load` fills in the model's default, so the queue never relies on implicit CLI defaults.
- **Escalation:** a task that fails is retried one tier up, `haiku` → `sonnet` → `opus` (`escalate_on_retry`). Once on `opus`, a retry raises the effort instead, for example `high` → `xhigh`.
- **Overrides:** a plan file is plain JSON, so you can change any task's model before `make load`. Proposals carry a model too, which you see in `make proposals`.
- **Guardrails:** workers can only use the aliases in `models.workers`, so a plan or proposal asking for anything else is rejected. Any configured model ID containing a word from `models.forbidden` (`fable`, `mythos`) stops the orchestrator before it starts.

`make status`, the dashboard and `.orch/events.jsonl` show which model ran each task, and the event log notes escalations.

### MCP servers

Each role gets only the MCP servers it needs. Agents run with `--strict-mcp-config`, so your personal MCP setup (IDE, docs connectors, …) never reaches them.

| Server | What agents use it for | Roles |
|---|---|---|
| **gopls** (v0.23.0, `gopls mcp`) | Go symbol search, references, package APIs, diagnostics, instead of grepping generated code | backend, tests, security |
| **Context7** (`@upstash/context7-mcp@4.3.0`) | Current docs for ogen, mongo-driver v2 and other libraries | api, backend |
| **MongoDB**, read-only (`mongodb-mcp-server@3.0.5`) | Inspect collections, documents, indexes and query plans | backend, security |

- **gopls** is built once into `.orch/bin` on the first `make run`.
- **MongoDB** starts only when `MONGO_TEST_URI` is set (`make mongo && export MONGO_TEST_URI=mongodb://localhost:27017`). It runs with `MDB_MCP_READ_ONLY=true`, telemetry disabled, and the `connect`/`export`/Atlas tools disabled, so agents can only read the configured local server.
- **Context7** works without a key; export `CONTEXT7_API_KEY` for higher rate limits.
- **Configuration:** servers are defined under `mcp_servers` in `config.json`, and assigned to roles under `mcp`. Placeholders: `{root}`, `{orch}`, `{env:NAME}`.

## Backend architecture

Every feature is a **bounded context** in `backend/internal/<context>/`, built as a hexagon:

| Layer | Contains | May depend on |
|---|---|---|
| `domain/` | aggregates, value objects, domain errors, repository interface | stdlib only |
| `app/` | `UseCases` interface (inbound port) + `Service` | its `domain` |
| `adapter/httpapi/` | implements the context's `oas.Handler` methods; maps oas ↔ domain and domain errors → HTTP | its `app`, `domain`, `oas` |
| `adapter/mongodb/` | implements `domain.Repository` on MongoDB 8 | its `domain`, `platform/mongodb`, the driver |
| `adapter/repotest/` | repository contract suite, run against the MongoDB repository | its `domain` |

- **Boundaries are tests:** `internal/archtest` fails on any import that breaks the rules, including one bounded context importing another.
- **Wiring:** only `internal/bootstrap` (the composition root) and `internal/handler` (which embeds the adapters) may reach into a context.
- **Spec-first:** operations in `openapi.yaml` without an implementation return 501, so the spec can merge before the code.
- **Errors:** domain errors are mapped to HTTP statuses by each adapter. Anything unmapped becomes a generic 500 and is logged. Every error response is `{"error": "…"}`.

## Running the app

```bash
make up          # docker compose: MongoDB 8 + backend on http://localhost:8000
make logs
make down        # keeps data in the mongo-data volume; `docker compose down -v` drops it

make mongo && make backend   # locally against the compose MongoDB
make check                   # all checks; needs MongoDB (make mongo)
```

Configuration (environment):
- `PORT` (8000): the port the server listens on.
- `LISTEN_HOST` (`127.0.0.1`): the IP address the server listens on. The image sets `0.0.0.0` so the published port works; docker-compose.yml publishes it on `127.0.0.1` only.
- `MONGO_URI` (`mongodb://localhost:27017`), `MONGO_DB` (`orch`). The server always connects to MongoDB and migrates before serving.
- `SEED_DEMO_DATA`: parsed with `strconv.ParseBool`; unset or invalid means off. When on, the 12 demo books are added at startup through the catalog use cases, after the migrations. Books whose ISBN is already present are skipped, so restarts don't duplicate them; deleted demo books come back, and edited ones are kept. The log line is `seeded N demo books, skipped M`.

docker-compose.yml deliberately leaves `SEED_DEMO_DATA` unset, so demo data stays off there; to turn it on for one run, use `SEED_DEMO_DATA=true make backend`.

**Books API:** `/api/books` has five operations: `POST` adds a book, `GET` lists them (filter with `author`, page with `limit` and `offset`), and `GET`, `PUT` and `DELETE` work on `/api/books/{id}`. `PUT` needs the `version` you last read; if the book has changed since, the answer is 409. The contract is in [`backend/api/openapi.yaml`](backend/api/openapi.yaml).

**Limits:** request bodies are capped at 64 KiB (413). Each client has a rate limit with separate read (50/s, burst 100) and write (5/s, burst 20) buckets; over the limit the API answers 429 with `Retry-After`. `/api/health` is exempt. Clients are keyed by remote IP, with IPv6 grouped by /64. `X-Forwarded-For` is ignored, so everyone behind Docker port mapping or a reverse proxy shares one bucket. The values are in `backend/internal/middleware/ratelimit.go` (`DefaultRateLimitConfig`).

## Tuning

- `orchestration/config.json`:
  - `max_workers`, `max_attempts`, `agent.timeout_s`, `lead.timeout_s`;
  - `lead.allowed_tools`: the lead engineer may read and run `git diff/log/show`, nothing else;
  - `models`: planner model, lead model (story review), reviewer model (review chat), worker models (aliases → IDs, optional `effort`), default, escalation, forbidden words;
  - `mcp_servers` and `mcp`: MCP servers and which roles get them;
  - `agent.allowed_tools`: agents run with `--permission-mode acceptEdits`, and Bash access is limited to `check.sh` and the `go`/`npm` commands listed there;
  - `require_tests_for`: the TDD rule;
  - `gates`: per-area gate commands. The `frontend` gate (`npm run typecheck && npm test`) is ready for when the Vue app exists.
- `orchestration/roles/*.md`: role prompts, passed with `--append-system-prompt`. To add a role, create `<role>.md` and use `"role": "<role>"` in tasks. `planner` and `lead` are run by the orchestrator itself and can't be given tasks.
- `CLAUDE.md`: the rules every agent reads.
