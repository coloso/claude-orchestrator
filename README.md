# orch-test: multi-agent orchestration demo

Several headless Claude Code agents build a Go API in parallel.
- **Backend:** designed with **DDD**, structured as a **hexagonal architecture**, written **test-first**, and stored in **MongoDB 8**.
- **API:** specified in OpenAPI 3, with server and client code generated by [ogen](https://ogen.dev).
- **Frontend:** Vue + TypeScript, coming later.

You describe a feature as a **story**. A planner agent breaks it into tasks, and worker agents implement them in parallel, each in its own git worktree. A quality gate checks every branch before the orchestrator merges it. You decide at a few checkpoints along the way.

## Quick start

Requires `python3`, `go` (1.27+), `git`, `claude` (Claude Code, logged in) and Docker.

```bash
git add -A && git commit -m "Initial scaffold"   # the orchestrator merges into your current branch and needs a clean tree

# Rehearse without calling Claude (no cost): fake agents, real queue, worktrees and merges
git switch -c dry-run && make dry-run
git switch main && git branch -D dry-run && make reset

# The real thing: the prepared todo plan (stories/S01-todo.md), 10 tasks
make demo        # watch it on http://localhost:8765/orchestration/dashboard/
```

## Using the orchestrator

The orchestrator is a Python CLI (`orchestration/orchestrator/orchestrator.py`, standard library only). The `make` targets are shortcuts for it, so use whichever you prefer:

| `make` | CLI (`python3 orchestration/orchestrator/orchestrator.py …`) | What it does |
|---|---|---|
| `make plan STORY=stories/S02-x.md` | `plan stories/S02-x.md` | The planner agent turns a story into a plan file, `orchestration/plans/S02-x.json`. Nothing is queued yet |
| `make load PLAN=orchestration/plans/S02-x.json` | `load <plan>` | Queues the plan's tasks |
| `make run` | `run [--workers N]` | Starts workers until nothing runnable is left; serves the dashboard |
| `make run ONLY=S02-01,S02-02` | `run --only S02-01,S02-02` | Runs only these tasks (e.g. the spec phase) |
| `make status` | `status` | Every task and its state; errors for failed ones |
| `make proposals` | `proposals` | Follow-up tasks agents proposed, e.g. security fixes |
| `make approve IDS="S02-07.1"` | `approve <ids>` | Queues proposals; they run on the next `make run` |
| `make reject IDS="S02-07.2"` | `reject <ids>` | Discards proposals |
| `make retry IDS="S02-03"` | `retry <ids>` | Puts tasks that used up their attempts back in the queue |
| `make reset` | `reset` | Deletes runtime state (`.orch/`, `.worktrees/`, `agent/*` branches). Keeps stories, plans and merged commits |
| `make demo` / `make dry-run` | `load` + `run [--fake]` | Prepared todo plan, for real or rehearsed |

### Workflow: story → plan → spec → implementation

You stay in charge at three checkpoints: the **plan**, the **spec** and the **proposals**. Between them, agents work in parallel without you.

```
 you          write story ──▶ review plan ──────────▶ review spec ─────────────▶ approve proposals ──▶ ship
                  │               ▲    │                 ▲    │                      ▲     │
 agents           └─ planner ─────┘    └─ phase 1: spec ─┘    └─ phase 2: adapters, ─┘     └─ fixes
                                          + domain model         storage, e2e, docs,
                                          + spec review          hardening review
```

1. **Write a story** in `stories/S<NN>-<slug>.md` (copy `stories/TEMPLATE.md`). The story describes the *what*, in the domain's language:
   - the user story;
   - the bounded context;
   - domain terms and rules;
   - acceptance criteria;
   - what's out of scope.
2. **Plan it:** `make plan STORY=…` writes `orchestration/plans/S<NN>-<slug>.json`, with task IDs `S<NN>-01`, `S<NN>-02` and so on. **Review it before anything runs.** Check that each task's scope is narrow, that the dependencies make sense, and that every acceptance criterion has a test. The file is plain JSON, so edit it as needed.
3. **Commit** the story and the plan (`run` needs a clean working tree), then `make load PLAN=…`.
4. **Phase 1, the spec:** `make run ONLY=<api task>,<model task>,<spec review>`. The domain model doesn't depend on the spec, so it is built test-first at the same time.
5. **Review the spec:**
   - `git show` the spec merge;
   - read `backend/api/openapi.yaml`;
   - read the security spec review in `docs/security/`;
   - run `make proposals`.

   This is the cheapest moment to change your mind. Edit the spec yourself (then `make generate` and commit), or approve the proposed spec fixes. Implementation tasks start from the merged code, so they pick up your changes.
6. **Phase 2, implementation:** `make run` runs everything else, including the HTTP adapter, MongoDB storage, e2e tests for the acceptance criteria, docs and the hardening review.
7. **Decide on proposals:** `make proposals`, then `approve` or `reject`, then `make run`. Repeat until nothing important is left.
8. **Ship:** `make check`, `make up`, try the API, and merge the branch.

**Variations**
- **Small story:** skip the spec checkpoint, `make load` and then a single `make run`.
- **API design session:** plan the story, then only ever run the api task and its spec review, and iterate on the spec with proposals until it's right.
- **Fix-up round:** for a bug, write a tiny story ("Given …, when …, then …") and plan it like any other.

### Example: a shopping list

**1. Story:** `stories/S02-shopping-list.md`

```markdown
# S02: Shopping lists

## Story
As a household member, I want shared shopping lists, so that we buy everything we need exactly once.

## Domain
- **Bounded context:** `shopping` (new)
- **Terms:** a *shopping list* has a *name* and *items*; an item has a *product name* and a *quantity*;
  items are *added*, *checked off* and *removed*; a list is *cleared* of checked-off items.
- **Rules:**
  - A list name is 1–100 characters; a product name 1–100 characters; quantity 1–99.
  - Adding a product that is already on the list increases its quantity instead of adding a duplicate.
  - Checked-off items can't change quantity.

## Acceptance criteria
- [ ] When I create a list "Weekend", then it exists with no items.
- [ ] When I add "Milk" ×2 and then "milk" ×1, then the list has one item "Milk" ×3.
- [ ] When I add an item with quantity 0 or 100, then I get 400.
- [ ] Given a checked-off item, when I change its quantity, then I get 409.
- [ ] When I clear the list, then only unchecked items remain.
- [ ] Unknown lists and items give 404.

## Out of scope
- Authentication, sharing permissions, prices.
```

**2. Plan:**

```bash
make plan STORY=stories/S02-shopping-list.md
```

The planner prints the plan it wrote. A typical result looks like this; yours will differ, which is why you review it:

```
Wrote 8 task(s) to orchestration/plans/S02-shopping-list.json:
  S02-01   [api]       Shopping list API spec
  S02-02   [backend]   Shopping domain model and use cases (TDD)
  S02-03   [security]  Security review: shopping spec  (after S02-01)
  S02-04   [backend]   Shopping HTTP adapter and wiring  (after S02-01, S02-02)
  S02-05   [backend]   Shopping MongoDB repository  (after S02-02, S02-04)
  S02-06   [tests]     E2E tests for the acceptance criteria  (after S02-04)
  S02-07   [security]  Security review: shopping context  (after S02-04, S02-05)
  S02-08   [docs]      Shopping list documentation  (after S02-04, S02-05)
```

Open the JSON and check it. For example: is the "merge duplicate products" rule in S02-02's prompt? Does S02-06 quote every acceptance criterion? Is S02-02's scope limited to `internal/shopping/{domain,app,adapter/memory}`?

**3. Commit and queue:**

```bash
git add stories/S02-shopping-list.md orchestration/plans/S02-shopping-list.json
git commit -m "S02: shopping list story and plan"
make load PLAN=orchestration/plans/S02-shopping-list.json
```

**4. Phase 1, spec and model:**

```bash
make run ONLY=S02-01,S02-02,S02-03
```

**5. Review the spec:**

```bash
git log --oneline -5                       # Merge S02-01 …, Merge S02-02 …, Merge S02-03 …
git show --stat HEAD~2                     # what the spec task changed
less backend/api/openapi.yaml
less docs/security/S02-03-*.md             # e.g. "SEC-1: listShoppingLists is unbounded"
make proposals
```

```
S02-03.1  [medium] Paginate listShoppingLists  — role api, from S02-03
    why:   SEC-1: unbounded list response
    …
```

```bash
make approve IDS=S02-03.1      # or: make reject IDS=S02-03.1, or edit the spec yourself and commit
```

**6. Phase 2, everything else** (S02-03.1 runs too, since it's now queued):

```bash
make run
```

**7. Proposals from the hardening review:**

```bash
make proposals                 # e.g. S02-07.1 [medium] Limit request body size
make approve IDS=S02-07.1 && make run
```

**8. Ship:**

```bash
make check                                       # all gates on the merged result
make up
curl -s -X POST localhost:8000/api/shopping-lists -d '{"name":"Weekend"}' -H 'Content-Type: application/json'
```

### Monitoring and troubleshooting

- **Dashboard:** http://localhost:8765/orchestration/dashboard/ while `run` is active. It shows agents, a task board, live tool calls and cost.
- **`make status`:** a failed task shows the gate or agent error.
  - **Attempts:** every task gets `max_attempts` (2), each in a fresh worktree.
  - **Retry:** after fixing the cause (an unclear prompt in the plan, a wrong scope, …), `make retry IDS=…` and then `make run`.
- **Logs:**
  - `.orch/logs/<task>.attempt<N>.jsonl` is the raw Claude stream (every tool call and its result);
  - `.orch/events.jsonl` is the orchestrator's event log.
- **Stuck queue:** `run` stops when nothing runnable is left. If tasks are still pending, a dependency failed; check `make status`.
- **Ctrl-C** stops the workers. Interrupted tasks go back to pending on the next `run`.
- **MongoDB adapter tests:** agents and gates inherit your environment. To have them run these tests, start the database and export `MONGO_TEST_URI` before `make run`:

  ```bash
  make mongo && export MONGO_TEST_URI=mongodb://localhost:27017
  ```

### Dry runs

`--fake` workers don't call Claude. They write a placeholder file inside each task's scope, skip the gate commands, and security tasks propose a fake follow-up. This exercises the queue, dependencies, `--only`, proposals and merges at no cost. The placeholders get merged, so use a throwaway branch:

```bash
git switch -c dry-run
make dry-run                                   # or: make load PLAN=… && python3 orchestration/orchestrator/orchestrator.py run --fake
git switch main && git branch -D dry-run && make reset
```

## How it works

### Layout

```
orch-test/
├── CLAUDE.md          rules every agent reads
├── docker-compose.yml MongoDB 8 + backend
├── stories/           your input: one story per feature (TEMPLATE.md, S01-todo.md, …)
├── backend/           Go 1.27 module                       ┐
│   ├── api/openapi.yaml   API contract (source of truth)   │
│   ├── internal/<context>/ bounded context = hexagon       │
│   ├── internal/oas/      ogen-generated server + client   │
│   ├── internal/handler/  embeds the contexts' adapters    │ the product
│   ├── internal/bootstrap/ composition root, storage choice│ agents work on
│   ├── internal/archtest/ dependency rules as a Go test    │
│   ├── internal/platform/mongodb/ MongoDB connection       │
│   ├── e2e/               tests via generated oas.Client   │
│   ├── Dockerfile         distroless image                 │
│   └── check.sh           every backend check (the gate)   │
├── frontend/          reserved for Vue 3 + TS              │
├── docs/              written by agents (docs/security/: reviews)
│
├── orchestration/     everything that runs the agents; agents never touch it
│   ├── config.json       workers, model, allowed tools, gates, TDD rule
│   ├── orchestrator/     Python 3 stdlib, no deps
│   │   ├── orchestrator.py   CLI: plan, load, run, status, proposals, approve, reject, retry, reset
│   │   ├── worker.py         claim task → `claude -p` in worktree → commit → gate → collect proposals
│   │   ├── tasks.py          file-based queue (atomic rename = claim)
│   │   ├── worktrees.py      one worktree + branch per task
│   │   └── quality_gate.py   scope check, TDD check, gate commands
│   ├── roles/            role prompts: planner, api, backend, tests, security, docs, frontend
│   ├── plans/            plan files: todo-tasks.json (demo), S<NN>-*.json from `make plan`
│   └── dashboard/        live view, served by the orchestrator
│
├── .orch/             runtime state (gitignored)
└── .worktrees/        agent checkouts (gitignored)
```

### Task lifecycle

```
proposed ──approve──▶ pending ──claim──▶ claimed ──agent + commit + gate ok──▶ passed ──merge──▶ done
   │                     ▲                  │                                     │
   └─reject─▶ rejected   └──── requeue ──── failed ◀──── gate / agent error ──────┘ (merge conflict)
```

- A task is claimable once every task in its `depends_on` is `done`, so dependent work always starts from merged code.
- Workers claim tasks atomically. Each task runs `claude -p` with the task's role prompt in a fresh worktree on branch `agent/<id>`. The orchestrator merges passing branches one at a time.
- Agents can't commit or touch anything outside their scope. Work they think is needed elsewhere becomes a **proposal**, which waits in `proposed` for you.

### Quality gate

Every task branch has to pass these checks before it's merged:

| Check | Where |
|---|---|
| Changed files are within the task's `scope` globs | `quality_gate.py` |
| TDD: a change in `internal/*/domain` or `internal/*/app` comes with a `_test.go` change in the same package | `quality_gate.py` (`require_tests_for` in `config.json`) |
| `internal/oas` matches the spec (no hand edits, no forgotten `go generate`) | `backend/check.sh` |
| gofmt, go vet | `backend/check.sh` |
| Tests, including `internal/archtest` (hexagonal and bounded-context dependency rules) | `backend/check.sh` |
| At least 80% coverage in domain and app packages (`MIN_COVERAGE`) | `backend/check.sh` |
| `gosec` (static analysis) and `govulncheck` (known vulnerabilities in called dependencies) | `backend/check.sh` |

Agents run `backend/check.sh` themselves before finishing, so most failures are fixed before the gate ever sees them. `make check` runs it on your checkout.

### Roles

| Role | Does | Typical scope |
|---|---|---|
| `planner` | Story → plan; never writes code | (none) |
| `api` | OpenAPI spec + `go generate` | `backend/api/**`, `backend/internal/oas/**` |
| `backend` | DDD model and use cases test-first, adapters, wiring | `backend/internal/<context>/…` |
| `tests` | e2e tests for the acceptance criteria, via the generated client | `backend/e2e/**` |
| `security` | Threat model, findings, security regression tests; fixes come back as proposals. Never blocks merges | `docs/security/**`, `backend/e2e/security_*_test.go`, infrastructure files |
| `docs` | Documentation from the actual code | `docs/**` |
| `frontend` | Vue 3 + TS (once `frontend/` exists) | `frontend/**` |

Authentication and authorization are out of scope for the demo. Security reviews record them once as an accepted risk.

## Backend architecture

Every feature is a **bounded context** in `backend/internal/<context>/`, built as a hexagon:

| Layer | Contains | May depend on |
|---|---|---|
| `domain/` | aggregates, value objects, domain errors, repository interface | stdlib only |
| `app/` | `UseCases` interface (inbound port) + `Service` | its `domain` |
| `adapter/httpapi/` | implements the context's `oas.Handler` methods; maps oas ↔ domain and domain errors → HTTP | its `app`, `domain`, `oas` |
| `adapter/memory/` | implements `domain.Repository` in memory (tests, default) | its `domain` |
| `adapter/mongodb/` | implements `domain.Repository` on MongoDB 8 | its `domain`, `platform/mongodb`, the driver |
| `adapter/repotest/` | repository contract suite, run against every repository adapter | its `domain` |

- **Boundaries are tests:** `internal/archtest` fails on any import that breaks the rules, including one bounded context importing another.
- **Wiring:** only `internal/bootstrap` (the composition root) and `internal/handler` (which embeds the adapters) may reach into a context.
- **Spec-first:** operations in `openapi.yaml` without an implementation return 501, so the spec can merge before the code.
- **Errors:** domain errors are mapped to HTTP statuses by each adapter. Anything unmapped becomes a generic 500 and is logged. Every error response is `{"error": "…"}`.

## Running the app

```bash
make up          # docker compose: MongoDB 8 + backend on http://localhost:8000
make logs
make down        # keeps data in the mongo-data volume; `docker compose down -v` drops it

make backend                              # locally, in-memory storage
make mongo && STORAGE=mongo make backend  # locally against the compose MongoDB
make test-mongo                           # all checks, including the MongoDB adapter tests
```

Configuration (environment): `PORT` (8000), `STORAGE` (`memory` or `mongo`), `MONGO_URI`, `MONGO_DB`, `CORS_ORIGIN`.

## Tuning

- `orchestration/config.json`:
  - `max_workers`, `max_attempts`;
  - `agent.model`, `agent.timeout_s`, and `planner.model`;
  - `agent.allowed_tools`: agents run with `--permission-mode acceptEdits`, and Bash access is limited to `check.sh` and the `go`/`npm` commands listed there;
  - `require_tests_for`: the TDD rule;
  - `gates`: per-area gate commands. The `frontend` gate (`npm run typecheck && npm test`) is ready for when the Vue app exists.
- `orchestration/roles/*.md`: role prompts, passed with `--append-system-prompt`. To add a role, create `<role>.md` and use `"role": "<role>"` in tasks.
- `CLAUDE.md`: the rules every agent reads.
